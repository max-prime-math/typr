You are working in the Typr repository at the repo root.

Goal of this phase:
Implement a true local git repository backend for each Typr project in browser storage. After this phase, each project should have an actual working tree plus `.git` data, even if remote sync and advanced merge UX are still incomplete.

Before editing, read the code carefully with special focus on:

- the new project/repo model introduced in Phase 1
- `src/app/App.tsx`
- `src/workspace/workspaceTree.ts`
- `src/terminal/projectFilesystemAdapter.ts`
- `src/terminal/browserBackend.ts`
- `src/terminal/types.ts`
- `src/storage/indexedDbStorage.ts`
- current `src/git/*`
- current `src/github/githubSync.ts`

Important context you must respect:

1. The old fake git staging/commit layer in `src/git/gitState.ts` / `src/git/localCommit.ts` is transitional and should be removed or replaced in this phase.
2. The target is "one project = one real git repo".
3. The browser environment cannot rely on host `git`, so this phase must implement a browser-resident git store and operations layer.
4. The project tree should already be filesystem-first after Phase 1.

Core implementation requirements:

A. Introduce a real repo backend abstraction

- Create a repo service layer, for example `src/git/repoBackend.ts` plus supporting modules.
- This layer must expose real repository operations:
  - init repo
  - discover/open repo
  - read HEAD/current branch
  - status
  - stage paths
  - unstage/reset index entries
  - commit with author/message
  - list branches
  - create/switch branch
  - log/history
  - read tracked files
- The UI and shell must depend on this abstraction, not on ad hoc state mutations.
- Choose and document the git engine deliberately. If using a library, keep all direct library calls inside the repo service layer and add a short note explaining why it works in this browser app.
- The repo service must return structured errors rather than throwing raw implementation/library errors into the UI.

B. Store real `.git` data in browser-managed storage

- Back the repo with persistent browser storage, preferably OPFS or another robust file-oriented storage path already used by the app.
- The working tree and `.git` data must belong to the project.
- Avoid keeping git state only in React state or only in an app-specific JSON structure.
- Keep `.git` protected from normal editor, workspace tree, and browser shell file operations.
- Do not reuse any storage code path that clears and rewrites the whole workspace root unless it explicitly excludes and preserves `.git`.
- Make repo initialization idempotent and crash-safe. A failed initialization must not corrupt the working tree or legacy project data.
- Define a recovery path for partially migrated repositories, such as re-open, re-index, or re-init with user confirmation.

C. Replace the fake staging/commit model

- Remove the pseudo-git committed snapshot/staged path system added earlier.
- Replace it with real index-backed staging and commit behavior.
- `git status`, `git add`, `git reset`, `git commit -m`, `git branch`, `git switch`, and `git log` in the browser shell must operate on the real repo backend.
- Validate commit messages and author identity. Provide deterministic default author config for local commits if the user has not configured one.
- Branch creation/switching must reject unsafe ref names and must not discard uncommitted changes unless the user explicitly confirms a safe strategy.

D. Make files the source of truth for repo state

- The repo backend must operate on the actual project file tree.
- Diagram and graph files must participate as normal files if they are inside the repo tree.
- Avoid hidden app-only commit manifests and avoid treating project metadata files as surrogate git history.
- Binary file content must round-trip without string conversion.
- File mode/symlink behavior should either be implemented correctly or explicitly reported as unsupported.

E. Keep the current app working

- Editor, preview, files pane, terminal, diagrams, and graphs must still work.
- The project tree shown in the UI must reflect real file state from the working tree.
- The terminal file operations must mutate the same working tree the repo backend sees.
- Status, branch, and log UI must not compute repository state synchronously during React render.
- Large-tree status/index/hash operations must run through an async boundary, preferably a Web Worker, and should be debounced/cancellable.

Implementation guidance:

- If a library is needed for browser git internals, choose a pragmatic one and integrate it cleanly behind your own abstraction.
- Do not scatter direct git-library calls throughout `App.tsx`.
- Keep `App.tsx` moving toward orchestration instead of owning all git behavior directly.
- Add tests around repository operations where practical.
- Do not add remote transport code in this phase unless it is needed to shape the local abstraction.
- Do not store tokens in the local repo config or in general git workspace state.

Non-goals for this phase:

- Do not finish remote push/pull/fetch here unless the repo abstraction naturally needs small hooks.
- Do not tackle advanced merge UI yet.
- Do not try to build a local agent backend in this phase.

   - `git status`

Required QA instructions for the human user:

After you finish and before declaring the phase complete, tell the user to test exactly this:

1. Open a project and make a small text edit to `main.typ`.
2. In the browser shell run `git status` and confirm the file shows as modified.
3. Run `git add main.typ`, then `git status`, and confirm it is staged.
4. Run `git commit -m "test commit"` and confirm `git log` shows the commit.
5. Edit the file again, confirm `git status` shows a new working-tree modification.
6. Create a new file from the Files pane or shell, stage it, commit it, and confirm it appears in `git log`.
7. Create a branch, switch to it, make a commit, and confirm the branch and log update correctly.
8. Reload the app and confirm git history/status persist.
9. Try to delete or edit `.git` from the browser shell and confirm it is blocked.
10. With an unstaged edit present, try switching branches and confirm the app protects the edit rather than silently losing it.
