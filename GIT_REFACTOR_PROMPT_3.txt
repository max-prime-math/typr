You are working in the Typr repository at the repo root.

Goal of this phase:
Replace the current GitHub Contents API sync model with real remote git operations layered on top of the true local repo backend. The app should stop thinking in terms of "push files directly to GitHub" and start thinking in terms of normal remote repository behavior.

Before editing, read carefully:

- the repo abstraction from Phase 2
- `src/github/githubSync.ts`
- `src/app/App.tsx`
- `src/terminal/browserBackend.ts`
- `src/terminal/types.ts`
- `src/storage/indexedDbStorage.ts`
- any current `src/git/*` modules

Current legacy behavior you must replace:

1. `githubSync.ts` talks to the GitHub Contents API file-by-file.
2. The app writes `.typr-project.json` as app metadata for sync bookkeeping.
3. Push/pull/sync in `App.tsx` are app-level workflows, not real remote git workflows.
4. Branch lists and commit lists are partly remote API summaries, not the local repo's own truth.

Critical transport constraint:

Before implementing Phase 3, prove the selected remote strategy in this browser environment. Browser-only smart-HTTP git to GitHub is generally blocked by CORS. Do not route user tokens through an arbitrary third-party CORS proxy. If direct git transport is not viable, choose one of these explicit strategies and document it before coding:

- a trusted same-origin/local-agent transport that performs real git network operations outside the browser sandbox
- a remote host that explicitly supports browser CORS for git transport with token auth
- a GitHub Git Database API adapter that reads/writes commits, trees, blobs, and refs on top of the local repo, while clearly documenting that it is not the Contents API path

What to implement:

A. Introduce a remote git service on top of the real repo backend

- Add a remote operations layer, for example:
  - fetch
  - pull
  - push
  - clone or attach remote
  - add/update remote config
  - inspect upstream tracking branch
- Remote operations must act on the real local repo, not on app-generated file lists.
- Remote operations must be transactional from the app's perspective: failed fetch/pull/push must leave local refs, index, working tree, and object database in a recoverable state.
- Remote progress and cancellation must be surfaced through the service layer so long operations do not freeze the UI.

B. Deprecate and remove the Contents API sync path

- Remove or isolate `githubSync.ts` so it is no longer the primary path for git sync.
- Eliminate any remaining dependence on `.typr-project.json` for normal remote behavior.
- If a compatibility shim is needed for migration, keep it temporary and clearly marked.
- Do not reimplement file-by-file Contents API push/pull under a different name. If using GitHub APIs, use git object/ref semantics through blobs, trees, commits, and refs.

C. Make GUI actions reflect real git semantics

- `Pull` should mean a real fetch/pull against the repo.
- `Push` should push commits from the local repo.
- `Sync` should become a thin composed operation over real fetch/pull/push semantics, or be removed if it is misleading.
- Branch and log views should come from the local repo and its remotes, not separate GitHub API summaries unless needed for remote discovery.
- Ahead/behind must be computed from commit graph/ref state, not from file timestamps or app metadata.
- Pull must protect dirty working trees and must not overwrite local changes without an explicit safe conflict flow.

D. Wire terminal commands to real remote behavior

- The browser shell should support the remote-relevant subset that is actually implemented:
  - `git remote -v`
  - `git fetch`
  - `git pull`
  - `git push`
  - `git branch`
  - `git switch`
  - `git log`
  - `git status`
- If some commands are unsupported in browser-only mode, report that honestly and keep the implementation behind the repo abstraction.

E. Keep token-based GitHub auth straightforward

- The current product direction prefers token auth over SSH.
- Preserve simple token-based setup in settings.
- Store non-secret repo config locally as before.
- Be deliberate about where tokens live and how they are used.
- Store tokens in a small credential module, separate from project/repo state. Passing tokens into git/network code should happen through a credential callback or request-scoped parameter, not by embedding them in repo config.
- Redact tokens in all UI, terminal output, errors, logs, remote URLs, and persisted diagnostic state.
- Never send tokens to an untrusted CORS proxy or telemetry endpoint.

F. Keep data migration safe

- Existing projects that were using the old GitHub sync settings should migrate into remote repo config cleanly.
- Existing local commit history created in earlier phases may need migration or reset logic; handle that deliberately and document it.
- Preserve the old GitHub config until the new remote config has been saved and verified.
- If legacy fake commits cannot be converted to real commits safely, keep them read-only as historical notes or explain the reset clearly; do not silently pretend they are real commits.

Non-goals for this phase:

- Do not attempt multi-user collaboration UX beyond normal git remote behavior.
- Do not implement every obscure git command.
- Do not add a local agent unless the transport proof shows browser-only remote git cannot meet reliability and security requirements. If it is required, keep the browser/local-agent boundary small and explicit.

Definition of done:

1. The app no longer pushes files one-by-one through the GitHub contents API as its main flow.
2. Remote operations are driven by the local repo backend.
3. The Git UI accurately reflects local branch, upstream, ahead/behind, and commit state as implemented.
4. Terminal remote commands reflect the same backend behavior.
5. The remote transport strategy is documented, including CORS/token constraints and why it is secure enough.
6. Tokens are isolated from repo/project state and redacted everywhere user-visible.
7. Pull/push/fetch failure tests demonstrate recoverable local state.
8. Typecheck and tests pass.

Required automated verification before you stop:

- `npm run typecheck`
- `npm test`

Required QA instructions for the human user:

After you finish and before declaring the phase complete, tell the user to test exactly this:

1. Configure a GitHub remote with a token.
2. Create a local commit and verify `git log` shows it.
3. Push the commit and confirm the remote repository receives it.
4. Make a new commit outside the app if your setup allows it, then pull/fetch in the app and confirm local history updates.
5. Verify branch switching still works after a fetch/pull.
6. Confirm that no `.typr-project.json` or equivalent app metadata file is required for normal remote operation.
7. Reload the app and confirm the remote and local repo state persist.
8. Trigger a failed push or fetch, for example with a bad token, and confirm local commits and working-tree files are unchanged.
9. Confirm terminal output and settings views do not reveal the token.
